# Тестовое задание

Нужно ускорить ночную синхронизацию сущностей из CRM в Postgres.
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.
Сейчас прогон делает отдельный запрос и commit на каждую сущность
и в конце ещё раз читает всю таблицу.
## Некоторые правила бизнес-логики
- Покупатель без логина пропускается.
- Покупатель ищется по id покупателя в CRM, иначе по логину среди уже сохранённых сделок.
  Если по логину нашлось больше одной записи, совпадение не используется.
- Сделка ищется по id сделки в CRM, иначе по логину среди покупателей.
  Если это две разные записи, они сливаются в ту, что нашли по сделке; вторая удаляется.
  Если не нашлось ничего, создаётся новая запись.
- После успешного полного прохода удаляются покупатели и вложенные
  сущности, которых не было в этой выгрузке, в том числе с «удалить» в имени.
- Если сбор прервался, удаление не запускается.
Падения и расхождения кода с этим списком нужно поправить.
Формат JSON в полях можно сохранить.
## Ограничения
- Python >= 3.9, Flask, SQLAlchemy, PostgreSQL.
- Celery, брокер и боевой API поднимать не нужно.
- Новые сервисы не добавлять. Схему хранения можно менять.
- Ночной прогон ищет покупателя и сделку по id CRM и по логину.
  Другие части системы ищут покупателя или сделку по точному логину и по названию.
  этот поиск писать не нужно, но выбранная схема должна его выдерживать.
  Также нужно поддерживать связь сделка-покупатель.
- Способ реализации на ваше усмотрение, правила выше обязательны.
Полный объём локально гонять не нужно: клиента CRM в репозитории нет.
Оцените память процесса и число запросов к Postgres на указанных цифрах.
## Результат
Ссылка на репозиторий и короткий README:
что было дорого, что изменено, что оставлено и почему.

## Что было дорого
- Отдельный запрос и commit на каждую сущность
- Хранение десятков тысяч объектов в ids_map 
- Поиск по jsonb через `@>` без индекса
- Чтение всей таблицы и правка jsonb-массивов по одному элементу на каждую вложенную сущность при чистке.

## Что изменено
- Схема: Покупатели и сделки хранятся в отдельных таблицах с отношением 1:M

  `external_id` - id из amoCRM - уникальный индекс.

  `login` - логин из amoCRM.

  `to_delete` - пометка для удаления необновленных строк.

  Остальные атрибуты также хранятся в JSONB как и ранее, однако `amo_customer` и `amo_lead`
  теперь одиночные объекты.

- Алгоритм записи батчами. Вначале `UPDATE ... SET to_delete=true` на обе таблицы.
  Покупатели и сделки отправляются на запись батчами по 1000; батч пишется 2-3 выражениями:
  один `SELECT ... IN (...)` ищет существующие строки, они обновляются одним
  `UPDATE ... FROM (VALUES ...)` (merge jsonb, снятие `to_delete`), новые вставляются при помощи
  `INSERT ... ON CONFLICT DO UPDATE`. Commit раз в батч.

  После успешного завершения - `DELETE ... WHERE to_delete=true` (сначала покупатели, потом сделки;
  осиротевшие сделки с `customer_id = NULL` удаляются вместе с ними).
  Если процесс прервался, удаление не запускается. `ids_map` и финальное чтение
  таблицы не нужны.

## Оценка на заданном объеме (20 тыс. покупателей + 50 тыс. сделок)

Запросов к Postgres - в худшем случае порядка 500: до 5 выражений на батч
покупателей, до 7 на батч сделок, включая слияние дублей (4 выражения на батч).
Потребление памяти зависит линейно от размера батча.
При BATCH_SIZE=1000 потребление составит до 150 МБ, из-за большого объема json-данных

## Что можно улучшить
Можно использовать вебхуки amoCRM для получения событий о добавлении, редактировании и удалении
пользователей и сделок, что позволит обновлять данные в БД сразу после добавления
и избежать повышенных нагрузок на БД и 429 ошибок при обращении к API.
